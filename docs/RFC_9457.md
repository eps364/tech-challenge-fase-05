## Introduction

This document describes the implementation of **RFC 9457: Problem Details for HTTP APIs** across our microservices architecture. RFC 9457 (which obsoletes RFC 7807) standardizes how HTTP APIs communicate error details in a structured, machine-readable format.

### Why Problem Details?

Traditional API error responses vary widely, making integration difficult and error handling fragile. Problem Details provides:

- **Standardized Format**: Consistent error structure across all services
- **Machine-Readable**: Parseable by API clients and middleware
- **Actionable Information**: Includes context needed to resolve issues
- **Extensibility**: Custom fields for domain-specific details
- **Interoperability**: Follows IANA-registered standard

### RFC 9457 vs RFC 7807

RFC 9457 (published July 2023) supersedes RFC 7807 with:
- Enhanced clarity on relative URI handling
- IANA registry for standardized problem type URIs
- Improved guidance for implementers

**Reference**: https://www.rfc-editor.org/rfc/rfc9457.html

## Overview

### Media Types

Problem Details are served with dedicated media types for client negotiation:

- **JSON Format**: `application/problem+json`
- **XML Format**: `application/problem+xml`

This implementation focuses on JSON format only.

### Example Problem Detail Response

```json
{
  "type": "https://api.example.com/problems/triage/invalid-risk-level",
  "status": 422,
  "title": "Invalid Risk Level",
  "detail": "The provided risk level 'extreme' is not valid. Allowed values: low, medium, high.",
  "instance": "/appointments/triage/abc123",
  "timestamp": "2024-12-15T10:30:45.123Z",
  "traceId": "4ba2b033-1234-5678-abcd-efg123456789",
  "correlationId": "req-2024-12-15-001"
}
```

HTTP Status Code: `422 Unprocessable Content`

## Standard Fields

RFC 9457 defines the following standard fields for all Problem Detail objects:

### `type` (URI Reference) - OPTIONAL

- **Description**: Identifies the problem type
- **Default Value**: `about:blank` (if omitted)
- **Purpose**: Provides semantic meaning beyond HTTP status code
- **Recommendation**: Use absolute URIs under your control (e.g., `https://api.example.com/problems/...`)

**Example**:
```json
"type": "https://api.example.com/problems/triage/invalid-risk-level"
```

### `status` (Integer) - OPTIONAL

- **Description**: The HTTP status code returned for this problem occurrence
- **Range**: 100-599
- **Purpose**: Conveys status code to consumers when HTTP headers unavailable (e.g., logged responses)
- **Note**: Generators MUST use the same status code in actual HTTP response

**Example**:
```json
"status": 422
```

### `title` (String) - OPTIONAL

- **Description**: Short, human-readable summary of the problem type
- **Characteristics**:
  - SHOULD NOT change between occurrences (except for localization)
  - Intended for developers and operators
  - Should be same for all occurrences of the same problem type
- **Localization**: Use `Accept-Language` header for language negotiation

**Example**:
```json
"title": "Invalid Risk Level"
```

### `detail` (String) - OPTIONAL

- **Description**: Human-readable explanation specific to this problem occurrence
- **Characteristics**:
  - Focuses on helping client correct the problem
  - Can vary from occurrence to occurrence
  - Should NOT be parsed by clients (use extensions instead)
- **Security**: Must not expose sensitive implementation details

**Example**:
```json
"detail": "The provided risk level 'extreme' is not valid. Allowed values: low, medium, high."
```

### `instance` (URI Reference) - OPTIONAL

- **Description**: Identifies the specific occurrence of the problem
- **Use Cases**:
  - Support/forensic reference: `https://example.com/logs/incidents/abc123`
  - Request identifier: `https://example.com/requests/def456`
  - Unique string identifier: `req-2024-12-15-001`
- **Dereference**: When resolvable, may provide additional problem context

**Example**:
```json
"instance": "/appointments/triage/abc123"
```

## Custom Extensions

Beyond RFC 9457 standard fields, this implementation includes custom extensions for operational visibility and debugging:

### `timestamp` (ISO 8601 String)

- **Description**: When the problem occurred on the server
- **Format**: ISO 8601 with millisecond precision (e.g., `2024-12-15T10:30:45.123Z`)
- **Purpose**: Correlate server logs with client-reported issues
- **Always Included**: Yes, for all problem details

**Example**:
```json
"timestamp": "2024-12-15T10:30:45.123Z"
```

### `traceId` (UUID String)

- **Description**: Unique identifier for this specific request/problem occurrence
- **Format**: UUID v4 (e.g., `4ba2b033-1234-5678-abcd-efg123456789`)
- **Scope**: Single request-response cycle
- **Generation**: Created by API Gateway or service entry point
- **Purpose**: Debug specific error occurrences in logs/monitoring
- **Always Included**: Yes, for all problem details

**Example**:
```json
"traceId": "4ba2b033-1234-5678-abcd-efg123456789"
```

### `correlationId` (String)

- **Description**: Links related requests across multiple services
- **Format**: Custom pattern (e.g., `req-YYYY-MM-DD-NNN`)
- **Scope**: Entire business transaction across service boundaries
- **Generation**: Created by gateway, propagated via headers (X-Correlation-ID)
- **Purpose**: Track business operations across distributed system
- **Always Included**: Yes, for all problem details

**Example**:
```json
"correlationId": "req-2024-12-15-001"
```

### Extension Naming Conventions

When adding domain-specific extensions:

- **Names**: Start with a letter, contain alphanumeric characters + underscore
- **Length**: 3+ characters recommended
- **Prefix**: Consider service-specific prefix for clarity
- **Compatibility**: Clients MUST ignore unknown extensions

**Example - Validation Error Extension**:
```json
{
  "type": "https://api.example.com/problems/auth/validation-error",
  "status": 400,
  "title": "Validation Error",
  "detail": "One or more validation errors occurred",
  "errors": [
    {
      "field": "email",
      "detail": "Email format is invalid",
      "pointer": "#/email"
    }
  ]
}
```

## Problem Type Registry

This section documents all custom problem type URIs implemented across services.

### General Gateway Problems

**Type URI Pattern**: `https://api.example.com/problems/gateway/...`

| Type URI | HTTP Status | Title | Description |
|----------|-------------|-------|-------------|
| `https://api.example.com/problems/gateway/service-unavailable` | 503 | Service Unavailable | Downstream service is unreachable or not responding |
| `https://api.example.com/problems/gateway/rate-limited` | 429 | Too Many Requests | Client exceeded rate limit |
| `https://api.example.com/problems/gateway/invalid-request` | 400 | Invalid Request | Request format or structure is invalid |

### Authentication Service Problems

**Type URI Pattern**: `https://api.example.com/problems/auth/...`

| Type URI | HTTP Status | Title | Description |
|----------|-------------|-------|-------------|
| `https://api.example.com/problems/auth/unauthorized` | 401 | Unauthorized | Missing or invalid authentication credentials |
| `https://api.example.com/problems/auth/forbidden` | 403 | Forbidden | Authenticated user lacks required permissions |
| `https://api.example.com/problems/auth/validation-error` | 400 | Validation Error | Invalid login credentials or registration data |
| `https://api.example.com/problems/auth/token-expired` | 401 | Token Expired | JWT token has expired |
| `https://api.example.com/problems/auth/invalid-token` | 401 | Invalid Token | JWT token is malformed or invalid |

### Appointment Service Problems

**Type URI Pattern**: `https://api.example.com/problems/appointments/...`

| Type URI | HTTP Status | Title | Description |
|----------|-------------|-------|-------------|
| `https://api.example.com/problems/appointments/not-found` | 404 | Appointment Not Found | Requested appointment does not exist |
| `https://api.example.com/problems/appointments/conflict` | 409 | Appointment Conflict | Time slot already booked or unavailable |
| `https://api.example.com/problems/appointments/invalid-time` | 422 | Invalid Appointment Time | Proposed time is in past or invalid |
| `https://api.example.com/problems/appointments/validation-error` | 400 | Validation Error | Appointment data validation failed |

### Triage Service Problems

**Type URI Pattern**: `https://api.example.com/problems/triage/...`

| Type URI | HTTP Status | Title | Description |
|----------|-------------|-------|-------------|
| `https://api.example.com/problems/triage/not-found` | 404 | Triage Record Not Found | Requested triage record does not exist |
| `https://api.example.com/problems/triage/invalid-risk-level` | 422 | Invalid Risk Level | Risk level is not recognized (low, medium, high) |
| `https://api.example.com/problems/triage/validation-error` | 400 | Validation Error | Triage data validation failed |
| `https://api.example.com/problems/triage/duplicate-entry` | 409 | Duplicate Triage Entry | Patient already has an active triage record |

### Medical Record Service Problems

**Type URI Pattern**: `https://api.example.com/problems/medical-records/...`

| Type URI | HTTP Status | Title | Description |
|----------|-------------|-------|-------------|
| `https://api.example.com/problems/medical-records/not-found` | 404 | Medical Record Not Found | Requested record does not exist |
| `https://api.example.com/problems/medical-records/access-denied` | 403 | Access Denied | User lacks permission to access record |
| `https://api.example.com/problems/medical-records/validation-error` | 400 | Validation Error | Record data validation failed |
| `https://api.example.com/problems/medical-records/conflict` | 409 | Conflicting Record | Record conflicts with existing data |

### Registry Service Problems

**Type URI Pattern**: `https://api.example.com/problems/registry/...`

| Type URI | HTTP Status | Title | Description |
|----------|-------------|-------|-------------|
| `https://api.example.com/problems/registry/not-found` | 404 | Registry Entry Not Found | Requested entry does not exist |
| `https://api.example.com/problems/registry/conflict` | 409 | Conflicting Entry | Entry conflicts with existing registry data |
| `https://api.example.com/problems/registry/validation-error` | 400 | Validation Error | Registry data validation failed |

## Implementation Guidelines

### HTTP Headers for Trace/Correlation IDs

Services MUST propagate trace and correlation IDs via HTTP headers:

```http
X-Trace-ID: 4ba2b033-1234-5678-abcd-efg123456789
X-Correlation-ID: req-2024-12-15-001
```

### Service-to-Service Error Handling

When service A calls service B and receives a Problem Detail:

1. **Extract Problem Details** from B's response
2. **Propagate Context**: Preserve traceId and correlationId
3. **Transform if Necessary**: Map B's problem type to A's context if needed
4. **Re-throw as Domain Exception**: Let A's GlobalExceptionHandler create final response

**Example**: API Gateway receives 404 from Appointment Service
```json
// From Appointment Service
{
  "type": "https://api.example.com/problems/appointments/not-found",
  "status": 404,
  "title": "Appointment Not Found",
  "detail": "No appointment found with ID: abc123",
  "instance": "/appointments/abc123"
}

// Gateway forwards with same traceId/correlationId but may enrich instance
{
  "type": "https://api.example.com/problems/appointments/not-found",
  "status": 404,
  "title": "Appointment Not Found",
  "detail": "No appointment found with ID: abc123",
  "instance": "/gateway/appointments/abc123",  // Updated for context
  "timestamp": "2024-12-15T10:30:45.123Z",
  "traceId": "4ba2b033-1234-5678-abcd-efg123456789",  // Preserved
  "correlationId": "req-2024-12-15-001"  // Preserved
}
```

### Exception-to-Problem Mapping

Create domain exceptions for each problem type, annotated with metadata:

```java
@ProblemType(
    type = "https://api.example.com/problems/triage/invalid-risk-level",
    title = "Invalid Risk Level",
    status = HttpStatus.UNPROCESSABLE_ENTITY
)
public class InvalidRiskLevelException extends DomainException {
    // Implementation
}
```

GlobalExceptionHandler automatically:
1. Catches domain exception
2. Reads @ProblemType metadata
3. Builds ProblemDetail with all fields
4. Returns RFC 9457-compliant response

### Content Negotiation

Always respond with correct media type:

```http
Content-Type: application/problem+json; charset=utf-8
```

### Security Considerations

**DO NOT** expose in error messages:
- Stack traces or implementation details
- Internal system architecture information
- Sensitive user data (passwords, tokens, PII)
- Database connection strings or query details

**DO** provide in error messages:
- Problem type URI (links to documentation)
- Instance identifier (for support reference)
- User-friendly guidance on how to resolve

## Examples

### Example 1: 401 Unauthorized (Missing Token)

**Request**:
```http
GET /api/appointments HTTP/1.1
Host: api.example.com
Accept: application/problem+json
```

**Response**:
```http
HTTP/1.1 401 Unauthorized
Content-Type: application/problem+json; charset=utf-8
X-Trace-ID: 4ba2b033-1234-5678-abcd-efg123456789
```

```json
{
  "type": "https://api.example.com/problems/auth/unauthorized",
  "status": 401,
  "title": "Unauthorized",
  "detail": "Missing authorization header. Please include 'Authorization: Bearer <token>' header.",
  "instance": "/api/appointments",
  "timestamp": "2024-12-15T10:30:45.123Z",
  "traceId": "4ba2b033-1234-5678-abcd-efg123456789",
  "correlationId": "req-2024-12-15-001"
}
```

### Example 2: 422 Unprocessable Content (Validation Error)

**Request**:
```http
POST /api/triage HTTP/1.1
Host: api.example.com
Content-Type: application/json

{
  "patientId": "patient123",
  "riskLevel": "extreme",
  "reason": "High fever"
}
```

**Response**:
```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json; charset=utf-8
```

```json
{
  "type": "https://api.example.com/problems/triage/invalid-risk-level",
  "status": 422,
  "title": "Invalid Risk Level",
  "detail": "The provided risk level 'extreme' is not valid.",
  "instance": "/api/triage",
  "timestamp": "2024-12-15T10:30:45.123Z",
  "traceId": "4ba2b033-1234-5678-abcd-efg123456789",
  "correlationId": "req-2024-12-15-001",
  "validValues": ["low", "medium", "high"],
  "providedValue": "extreme"
}
```

### Example 3: 404 Not Found

**Request**:
```http
GET /api/appointments/nonexistent HTTP/1.1
Host: api.example.com
```

**Response**:
```http
HTTP/1.1 404 Not Found
Content-Type: application/problem+json; charset=utf-8
```

```json
{
  "type": "https://api.example.com/problems/appointments/not-found",
  "status": 404,
  "title": "Appointment Not Found",
  "detail": "No appointment found with ID: nonexistent",
  "instance": "/api/appointments/nonexistent",
  "timestamp": "2024-12-15T10:30:45.123Z",
  "traceId": "4ba2b033-1234-5678-abcd-efg123456789",
  "correlationId": "req-2024-12-15-001"
}
```

### Example 4: 409 Conflict (Duplicate Entry)

**Request**:
```http
POST /api/appointments HTTP/1.1
Host: api.example.com
Content-Type: application/json

{
  "patientId": "patient123",
  "dateTime": "2024-12-20T14:30:00Z"
}
```

**Response**:
```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json; charset=utf-8
```

```json
{
  "type": "https://api.example.com/problems/appointments/conflict",
  "status": 409,
  "title": "Appointment Conflict",
  "detail": "The requested time slot is already booked. Available slots: 2024-12-20 14:45, 15:00, 15:15",
  "instance": "/api/appointments",
  "timestamp": "2024-12-15T10:30:45.123Z",
  "traceId": "4ba2b033-1234-5678-abcd-efg123456789",
  "correlationId": "req-2024-12-15-001",
  "conflictingResourceId": "apt-existing-123",
  "availableSlots": [
    "2024-12-20T14:45:00Z",
    "2024-12-20T15:00:00Z",
    "2024-12-20T15:15:00Z"
  ]
}
```

## Appendix: Migration from RFC 7807

This implementation is based on RFC 9457 (published July 2023), which obsoletes RFC 7807 (published March 2016).

### Key Changes from RFC 7807 to RFC 9457

1. **IANA Registry**: New registry established for common problem type URIs
2. **Relative URI Guidance**: Clarified handling and recommendations for relative URIs
3. **Multiple Problems**: Enhanced guidance for situations with multiple errors
4. **Localization**: Better support for language negotiation via Accept-Language

### Full Migration Notes

- **Status**: Complete replacement (RFC 7807 format no longer used)
- **Backwards Compatibility**: New format only; clients MUST update error parsing
- **Timeline**: Deployed across all services on [deployment date]
